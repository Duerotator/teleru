# выпуск релизов

руководство для мейнтейнеров. релизы собираются и публикуются автоматически через GitHub Actions с использованием секретов репозитория, поэтому контрибьюторы никогда не выпускают релизы вручную. эта страница описывает процесс выпуска и проверки релизов.

## версии

- релиз получает тег `<UPSTREAM>-tele.<N>`, например `v7.3.3-tele.23`, и заголовок `tele N · <тег апстрима>`.
- `N` на единицу больше максимального существующего релиза или тега независимо от используемого апстрима: нумерация продолжается при смене базы (`v7.3.1-tele.22` сменяется `v7.3.3-tele.23`), поскольку приложение сравнивает номера сборок. `build.yml` выбирает его автоматически либо принимает входной параметр `number`, если он выше всех существующих.
- `N` компилируется в код как значение `TELE_BUILD`. приложение отображает его как `tele #N` в заголовке окна и `сборка #N` в главном меню.
- автоапдейтер упорядочивает сборки сначала по версии апстрима `AppVersion`, а затем по `N`, поэтому релиз на базе более нового тега апстрима всегда имеет приоритет.

## ветки

- основная работа ведется в ветке `next`. pull request'ы направляются туда.
- `main` — ветка релизов: пуш в `main`, затрагивающий `UPSTREAM`, `patches/`, `tele.py`, `ci/` или `build.yml`, запускает сборку, которая публикует каждую платформу по мере готовности (см. [поэтапные релизы](#поэтапные-релизы)).

## перед выпуском релиза

1. **объединение (fold).** сопутствующие исправления и доработки функции объединяются в исходный патч функции там, где результат совпадает, сохраняя структуру «один патч на функцию». изменения, которые невозможно объединить начисто, остаются отдельными патчами.
2. **базовая линия (baseline).** после объединения запишите предыдущий релиз, объединенный тем же образом, в `ci/baselines.json`: его тег сопоставляется со словарем `{subject: sha256 измененных строк}` каждого патча. это гарантирует корректное сравнение в release notes без ложных срабатываний об удалении патчей. для следующего релиза она больше не потребуется.
3. **строки патчей.** каждый новый патч имеет свою строку в `docs/releases.md`, ссылки `вместе с N` указывают на верные номера, а общее число патчей в счетчике совпадает с реальностью. `docs/features.md` генерируется на основе этих данных.
4. **тестовое наложение.** экспортированная очередь проверяется на чистом клоне тега `UPSTREAM` командой `python tele.py --tdesktop <чистый клон> apply`.
5. **тестирование.** новые и измененные функции проверяются в локальной тестовой сборке. прогон в CI занимает часы, а сломанный релиз мгновенно попадает к пользователям через автоапдейтер.

## сборка и публикация

релиз собирается один раз и публикуется из готовой сборки, гарантируя отправку именно протестированных артефактов:

1. запустите `build.yml` на ветке с параметром `publish=false`. он соберет сборки для Windows, Linux и macOS и сохранит артефакты на 24 часа.
2. после успешного завершения переведите `main` на тот же коммит без повторной компиляции и опубликуйте прогон:

   ```
   gh workflow run build.yml --ref main -f from_run=<run id> -f publish=true
   ```

   параметр `publish` проверяет успешность прогона, совпадение `UPSTREAM`, `patches/` и `tele.py` с веткой `main` и использует номер релиза, выбранный этим прогоном. все три платформы уже собраны, поэтому публикуются практически одновременно.

workflow `promote.yml` умеет выполнять шаг 2 самостоятельно: если переменная репозитория `PROMOTE_RUN` содержит ID прогона, публикация стартует сразу после завершения сборки.

публиковать можно только прогон, успешно собравший все три платформы. запуск с `publish=false` или подмножеством `platforms` ничего не публикует, а `from_run` отклоняет запуск, если артефакты любой платформы отсутствуют или просрочены.

## поэтапные релизы

релиз выходит поэтапно для каждой платформы. у каждой платформы есть собственная задача публикации, стартующая сразу после завершения её сборки, поэтому пользователям Windows не приходится ждать более длительную сборку для macOS:

1. первая опубликованная платформа создает релиз с кратким текстом (`tele N выходит в релиз. готово: windows. собирается: linux, macos.`), файлом `tele-changelog.json` и **каналами-заглушками** для ещё не собранных платформ (копиями `tele-update-<platform>.json` предыдущего релиза). они подписаны и указывают на zip-архивы предыдущей версии, благодаря чему клиенты видят статус «актуальная версия» вместо ошибки отсутствия канала. релиз становится `latest` только после того, как готовы все каналы.
2. затем каждая платформа добавляет свои файлы и заменяет заглушку настоящим подписанным каналом. если две платформы завершаются одновременно, настоящие каналы всегда перезаписывают заглушки, предотвращая рассинхронизацию. краткий статус обновляется при каждом добавлении.
3. когда все три платформы опубликованы, задача `announce` формирует полные release notes, закрывает issues `build-failure` и `new-upstream` и публикует анонс в telegram-канале. описание и анонс сравниваются с предыдущим релизом, зафиксированным в начале запуска.

при сбое сборки платформы остальные платформы остаются опубликованными, а пользователи сбойной платформы сохраняют предыдущую версию через заглушку. сбой открывает issue `build-failure` и отправляет уведомление. повторный запуск упавших задач собирает и публикует недостающую платформу, после чего выпускает анонс.

## публикуемые файлы

| файл | описание |
|---|---|
| `tele-<tag>-win64.zip` | исполняемый файл `tele.exe` (Windows x64) |
| `tele-<tag>-linux64.zip` | бинарный файл `tele` (Linux x64) |
| `tele-<tag>-macos.zip` | приложение `tele.app` (подписанное ad-hoc для встроенного апдейтера) |
| `tele-<tag>-macos.dmg` | DMG-образ для ручной установки на macOS |
| `tele-update-win64.json`, `tele-update-linux64.json`, `tele-update-macos.json` | подписанные каналы обновлений (во время сборки — каналы предыдущего релиза) |
| `tele-changelog.json` | список изменений для показа в служебном чате внутри приложения |

после публикации всех платформ release notes содержат список новых, измененных и удаленных патчей со строками из `docs/releases.md`, ссылки на загрузку и полную таблицу патчей. если настроены секреты для анонсов, релиз публикуется в канале: новые и измененные патчи группируются по категориям окна «что нового», затем перечисляются удаленные. пост озаглавлен `tele for desktop <номер> · <версия tdesktop>` и завершается тегом `#desktop`.

релиз, который переходит на более новую версию tdesktop, открывает описание изменений, публикацию в канале и окно «что нового» в приложении разделом `telegram desktop <версия>`: строки из собственного `changelog.txt` апстрима для каждой версии после предыдущего релиза (включая бета-версии, от старых к новым). строки об опциях сборки опускаются. если changelog недоступен, выводится строка перехода «moved from».

## подпись и подтверждение подлинности

- **каналы обновлений.** каждый канал содержит имя релиза, номер сборки, URL zip-архива и контрольные суммы SHA-256 архива и исполняемого файла. канал подписывается ключом Ed25519, хранящимся исключительно в секретах репозитория; подпись проверяется открытым ключом `ci/update-public-key.pem` перед созданием релиза. открытый ключ встроен в клиент, поэтому приложение отклоняет неподтвержденный канал, несовпадающие хэши и ссылки вне релизов данного репозитория.
- **отладочные символы.** релизы для Linux и macOS также включают `tele-<tag>-<platform>-symbols.zip` — таблицу символов несконфигурированного бинарника. они требуются только для расшифровки адресов в crash dump в имена функций. для Windows символы не формируются из-за лимитов памяти и диска раннеров GitHub Actions.
- **подтверждение подлинности (build provenance).** каждый архив zip и dmg заверяется в задаче, собравшей его, через GitHub `actions/attest`. для macOS это задача объединения arm64 и x86_64 в универсальное приложение с последующей подписью. подтверждение остается валидным при публикации из готового прогона. любой желающий может проверить подлинность загрузки:

  ```
  gh attestation verify tele-<версия>-win64.zip --repo Duerotator/teleru
  ```

## новые релизы апстрима

workflow `sync.yml` каждые 3 часа проверяет наличие нового стабильного релиза tdesktop. бета-версии пропускаются.

- если очередь накладывается чисто, workflow обновляет `UPSTREAM`, коммитит `chore: bump upstream to <tag>`, запускает сборку с `publish=false` и открывает issue `new-upstream` с готовой командой для публикации.
- при возникновении конфликтов открывается issue `patch-conflict` с логом. конфликт разрешается локально, как описано в [руководстве по разработке](development.md#синхронизация-с-новым-релизом-апстрима), и никогда в CI.

workflow `canary.yml` ежедневно применяет очередь патчей к ветке `dev` апстрима и создает issue `canary-conflict` при сбоях, позволяя узнать о конфликтах заранее.

сбойный или отмененный запуск на `main` открывает issue `build-failure`, который закрывается следующим успешным релизом.

## кэши CI

сборки повторно используют результаты предыдущей компиляции без изменения итогового бинарника:

- **библиотеки Windows** сохраняются в кэше Actions с ключом по Windows SDK и `prepare.py`.
- **объектные файлы Windows и Linux** кэшируются через ccache (Windows: фиксированный релиз ccache, до 3 ГБ на ветку; Linux: сохраняется из `main`). исходники с макросами `__DATE__` или `__TIME__` всегда перекомпилируются заново для сохранения точной даты сборки.
- **macOS** собирает архитектуры arm64 и x86_64 параллельно и объединяет их утилитой `lipo`. архитектурно-независимые файлы идентичны. библиотеки macOS и среда сборки Linux размещены в ghcr.
